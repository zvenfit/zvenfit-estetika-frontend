# ADR-002: автоматические версии проверенных production-деплоев

Дата: 2026-09-26. Статус: принято для реализации; включение после merge отдельно.

## Контекст

Production workflow уже проверяет код, разворачивает функцию и сайт и выполняет
безопасный smoke. Теги и GitHub Releases отсутствуют: удачная выкладка не получает
постоянного номера. Ручная публикация требует помнить дополнительный шаг.
Основа переноса — [ZvenFit PR #73](https://github.com/zvenfit/zvenfit-frontend/pull/73).

## Решение

- Добавить release job после `smoke-production` только на `main`, с
  `contents: write` через `GITHUB_TOKEN` и без облачных полномочий.
- Checkout, тег и release notes привязывать к `github.sha` запуска; все jobs
  остаются в одной последовательной concurrency-группе деплоя.
- Начать с `v0.1.0` при отсутствии стабильных тегов. После первого релиза повышать
  patch по умолчанию, minor при `feat`, major при явном breaking-маркере.
  Учитывать весь ещё не выпущенный диапазон, исключая архивные и prerelease-теги.
- Проверять точный commit удалённого тега перед публикацией. Повтор после
  частичного сбоя использует тот же тег; готовый release не изменяет.
- Не назначать новую версию старому или расходящемуся коммиту после более нового
  тега. Восстановленный старый release не становится latest.
- Ограничить ручной production workflow веткой `main`, чтобы выкладка вне неё
  не обходила принятый релизный цикл.

## Альтернативы и последствия

Ручные теги сохраняют риск пропуска. Публикация перед деплоем может обозначать
неудавшуюся выкладку. Отдельный release workflow усложняет доказательство связи
со smoke и не нужен для текущего процесса. Изменение `package.json` ботом создаёт
лишний коммит и не требуется приватному статическому сайту.

Неуспех публикации оставляет уже развёрнутый сайт рабочим и помечает workflow
ошибкой до повторного запуска release job. Версия фиксирует исходники и успешную
проверку, но не является системой отката или гарантией последующего здоровья сайта.
Staging, схема БД, уведомления и облачные permissions этим решением не меняются.

Проверяемые свойства: первый релиз и его восстановление, правила версий,
расхождение истории, annotated tags, конкурирующие теги, отсутствие повторных
записей, сохранение latest и обязательная цепочка deploy → smoke → release.
Порядок эксплуатации — [релизный runbook](../releases.md).
