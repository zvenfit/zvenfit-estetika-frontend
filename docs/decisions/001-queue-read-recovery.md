# ADR-001: восстановление чтений outbox и отложенный проход worker

Дата: 2026-09-25. Статус: принято для реализации; production rollout отдельно.

## Контекст

Временные ошибки YDB session/query прерывают фоновую обработку долговечной очереди.
Ограничение тремя попытками может исчерпаться раньше общего deadline, а одиночный
отказ SELECT вызывает тот же runtime alert, что неизвестная ошибка приложения.
В Estetika обе разновидности уведомлений хранятся в отдельном transactional outbox;
отказ его чтения сам по себе не меняет запись заявки или согласия рассылки.

Источники: [разбор инцидентов](../monitoring-review-2026-09-24.md),
[аудит паритета](../upstream-review-2026-09-25.md),
[upstream PR #72](https://github.com/zvenfit/zvenfit-frontend/pull/72).

## Решение

1. Повторять только два SELECT очереди с одним монотонным deadline и общим
   AbortSignal. Паузы растут с 500 мс до 2 секунд, jitter до 50%; общий бюджет
   `min(2 × query timeout, 20000)` ограничивает и внутренние повторы SDK.
   Estetika сохраняет query timeout 10 секунд. Подготовка клиента выполняется
   до этого бюджета со своей политикой; общий driver не пересоздаётся при отмене.
2. Выполнение повторов принадлежит `ydb/read-operation.ts` и `ydb/read-retry.ts`.
   `observability/ydb.ts` измеряет результат и получает уведомления о запланированном
   и начавшемся повторе. Безопасный `prior_error` снимается до backoff.
3. YDB adapter переводит в `QueueReadUnavailableError` только явно временные
   ошибки двух чтений. Эта ошибка находится на уровне application/storage port;
   worker не импортирует YDB-коды или SDK. Неизвестные и постоянные ошибки
   отклоняют invocation. Сохранённый в памяти `cause` не позволяет маскировать
   неизвестную причину истечением бюджета во время паузы. Причина прошлой
   попытки не становится фазой текущего deadline.
4. `application/retry-worker.ts` возвращает deferred-result для временного
   отказа чтения и полагается на следующий минутный timer. Такой проход
   не выдаёт успешный heartbeat или вымышленные queue gauges. При отказе health
   после доставки её сохранённый статус остаётся действительным.
5. Добавить независимый log aggregate и критический alert на три deferred-прохода
   в десятиминутном окне. Сохранить runtime, storage, terminal delivery, heartbeat,
   backlog и trigger coverage. Успешные retries и slow query — INFO/email без повторов.

## Последствия и границы

- Два вида уведомлений используют один механизм восстановления; заявки,
  opt-in/consent state, lease и delivery token сохраняют прежнюю семантику.
- HTTP persistence, транзакции, claim/mark и Telegram POST не получают новых
  автоматических повторов и не используют deferred как успешное сохранение.
- При кратком отказе может увеличиться задержка до следующего минутного timer:
  платформа считает deferred успешным invocation и не запускает его error retry.
- Частые быстрые сбои допускают больше попыток внутри прежних 20 секунд.
  Backoff ограничивает частоту; длительный YDB-инцидент по-прежнему требует диагностики.
- Новый metric/alert должен быть применён до rollout worker. Git desired state
  не означает live-синхронизацию. Порядок внедрения и откат — в [runbook](../monitoring.md).
- Session traces служат локализации отказа, метрики длительности остаются query-only.
  Проекту не нужны новые сервисы, схема базы, staging adapters или message broker.

## Рассмотренные альтернативы

- Оставить три попытки: сохраняет прежний шум runtime и обрывает быстрые серии
  отказов при ещё доступном бюджете.
- Просто ослабить runtime alert: скрывает неизвестные ошибки и не даёт отдельного
  сигнала повторяющихся проблем чтения.
- Превращать любую ошибку в deferred: маскирует конфигурационные/программные
  дефекты. Поэтому классификация для deferred строже классификации для retry.
- Увеличить timeout или пересоздавать driver: не подтверждено анализом причины;
  teardown общего driver может затронуть независимую транзакцию.

## Проверяемые свойства

Реальный SDK с синтетическим транспортом проверяет восстановление на четвёртой
попытке, deadline и независимую транзакцию доменных данных/outbox. Handler-тесты
покрывают оба типа уведомлений, длительный отказ, восстановление, неуспешный health
после доставки, ошибки записи и отсутствие ложного heartbeat. Contract/drift-тесты
связывают события, selectors, 15-ID allowlist и правила уведомлений.
